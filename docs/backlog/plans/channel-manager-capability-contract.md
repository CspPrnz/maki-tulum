# Channel-manager capability contract — Hosthub vs Hostaway

Research only. This document does not decide a vendor. It exists so Felix can run a sandbox trial and make the decision cheaply, instead of inferring capability from marketing pages.

## Goal

After this lands, Felix has: (1) an outcome-level contract the winning vendor must satisfy, independent of either vendor's specific API shape; (2) what's provable from public docs today vs. what needs a live sandbox account; (3) a concrete sandbox test script; (4) the cost of guessing wrong on each capability.

## Why now

MRT-15-P0-02/P0-03 found that Phase 2 is about to freeze an availability/rates schema whose correctness depends on the channel manager's actual semantics — not the adapter interface, which only hides _syntax_ differences, not semantic ones (double-booking conflict resolution, whether guest PII survives the vendor, currency rounding rules). MRT-15-P1-07 found the EN/ES/DE + USD/EUR/MXN + WhatsApp journey has never been checked as one path across vendors. Getting this contract wrong is expensive later: it's baked into `services/api/src/db/schema.ts` and the Phase 2 booking/quote endpoints.

## 1. Outcome-level capability contract

Testable assertions, not features. "Must" = if unmet, do not proceed with that vendor without a documented workaround and Felix's sign-off.

| #   | Assertion                                                                                                                                                                                                                                   | Why it matters                                                                                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | A direct-site availability write (block/unblock) is readable back from the vendor within a bounded, documented latency (target: seconds, not the "1–4 hour iCal drift is catastrophic" window ADR 0004 already rejected).                   | Direct site is source of truth (`idea-v3.md` §9); a slow write window reopens the double-booking risk ADR 0004 exists to close.                                                                                                                                  |
| A2  | When a direct booking and an OTA booking race for the same date range, the vendor has a defined, observable conflict-resolution behavior (reject one, flag both, last-write-wins) — not silent overwrite.                                   | This is the literal double-booking failure mode named in `idea-v3.md` §13 ("Channel sync breaks, double-booking happens... Catastrophic for a single-unit owner").                                                                                               |
| A3  | Rate pushes support seasonal tables, LOS discounts, and per-date orphan-gap overrides at day granularity, and these are reflected in the vendor's own guest-facing surfaces (if it runs a booking engine) without re-derivation.            | `idea-v3.md` §9 "Calendar & channel" and `implementation-plan.md` Phase 2 rate engine are non-negotiable must-haves.                                                                                                                                             |
| A4  | Our Postgres can remain the sole source of truth for inventory and rates — i.e., the vendor accepts pushed state and does not require us to read its calendar as authoritative for direct-site display.                                     | Contradicts this and the whole "direct is source of truth" architecture (`implementation-plan.md` §4 Phase 3) is void.                                                                                                                                           |
| A5  | OTA-originated bookings arrive via webhook (push) with a documented retry/latency SLA; a polling fallback exists for webhook outages.                                                                                                       | `implementation-plan.md` Phase 3 exit criterion: "a booking made on Airbnb sandbox appears in our Postgres within 5 minutes." Pure polling cannot reliably hit this.                                                                                             |
| A6  | Cancellations and modifications from any channel propagate to us with the same latency/webhook guarantee as new bookings, including partial modifications (date change, guest count).                                                       | Silent cancellation drift re-opens double-booking risk from the other direction (a cancelled OTA night not reopened for direct sale).                                                                                                                            |
| A7  | Rates/quotes can be expressed and pushed/read in USD, EUR, and MXN without the vendor forcing a single settlement currency onto guest-facing display.                                                                                       | ICP requires USD/EUR/MXN display (`idea-v3.md` §9); MRT-15-P1-07.                                                                                                                                                                                                |
| A8  | **Existential**: for both OTA-originated and direct bookings routed through the vendor, the reservation payload the vendor gives us contains the guest's real (non-proxied) email and/or phone number, not a platform-masked relay address. | MRT-15-P1-01 — the north-star metric requires a first-party cross-channel identity graph. No vendor in the stack (`CONTEXT.md` Vendors table) owns this; if the channel manager also fails to surface it, the metric is unmeasurable by design, not by omission. |

**Bottom line on the public-docs pass:** Hostaway is the only one of the two with a genuinely public API reference; even so, the two capabilities that matter most for this project's thesis — A2 (conflict semantics) and A8 (real guest contact) — are unanswered for Hostaway too. This confirms MRT-15-P0-03's finding: the adapter pattern hides syntax, not the semantic gaps that actually decide the outcome.

## 3. Sandbox acceptance test plan

Run against a trial/demo account for each vendor before signing. Each step maps to a numbered assertion above. Do this before Phase 2's availability/rates schema is frozen, not after (MRT-15-P0-02).

| Step | Action                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Assertion(s) proven                                                                          |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 1    | Create one test listing per vendor. Set currency to USD; confirm whether EUR and MXN can be added as guest-facing display currencies (not just settlement currency).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | A7                                                                                           |
| 2    | Push an availability block via the API for a specific date range. Poll the read endpoint every few seconds until it reflects the block; record elapsed time.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | A1                                                                                           |
| 3    | Fire two near-simultaneous booking attempts for the same date range: one via the vendor's own test/OTA-simulated booking path, one via a direct API push simulating our checkout. Observe: which wins, whether a webhook or error fires for the loser, whether any window exists where both appear valid.                                                                                                                                                                                                                                                                                                                                                                  | A2                                                                                           |
| 4    | Push a seasonal rate table, a 7+-night LOS discount, and a manual 1–2 night orphan-gap override for a specific date pair. Confirm each is readable back and (if the vendor renders its own booking widget) visibly reflected there.                                                                                                                                                                                                                                                                                                                                                                                                                                        | A3                                                                                           |
| 5    | With our own webhook receiver stubbed (even a request-bin equivalent), create a booking through the vendor's OTA-simulated/test channel path. Confirm a webhook fires, record latency against the vendor's documented SLA, and inspect the payload for guest email/phone — is it the real address or a proxy?                                                                                                                                                                                                                                                                                                                                                              | A5, A8 (OTA path)                                                                            |
| 6    | Create a _direct_ test booking (guest enters their own contact details, routed through the vendor if the vendor's booking engine is in the direct path) and inspect the same payload for guest email/phone.                                                                                                                                                                                                                                                                                                                                                                                                                                                                | A8 (direct path) — this is the case that actually matters for the north-star identity graph. |
| 7    | Cancel one booking and modify another (change dates or guest count). Confirm both changes propagate via webhook within the same SLA window as creation, and confirm calendar state reopens correctly (the cancelled night becomes bookable again).                                                                                                                                                                                                                                                                                                                                                                                                                         | A6                                                                                           |
| 8    | Disable/break the webhook receiver deliberately. Confirm the vendor either retries per its documented policy or that a polling/reconciliation endpoint recovers the missed event without manual intervention.                                                                                                                                                                                                                                                                                                                                                                                                                                                              | A5 (fallback)                                                                                |
| 9    | End-to-end guest journey: complete one full booking in each of EN, ES, DE (if the vendor's own booking UI is in the path — otherwise confirm it's irrelevant because our own Next.js checkout owns the UI and the vendor only receives the resulting reservation), with quote display in USD, then EUR, then MXN, confirming FX rounding and no silent total change between display and confirmation (this is also the MRT-15-P1-08 quote-integrity invariant, worth checking here since the vendor is in the money path). Trigger a WhatsApp-relevant event (booking confirmed) and confirm it does not collide with or duplicate whatever we build via Brevo (ADR 0012). | A7, MRT-15-P1-07, MRT-15-P1-08                                                               |
| 10   | Run our planned weekly integrity check (compare our Postgres to the vendor's calendar) against the state left over from steps 1–9. Confirm no drift, or a fully explained drift.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | A1, A4                                                                                       |

**Human-owned:** Felix runs this test plan personally in each vendor's trial account (accounts, any card-on-file decision, and the actual booking flow require his login). No agent can execute steps 1–10 without vendor credentials.

## 4. What breaks if each capability is missing

| Capability missing                  | Cost if we pick a vendor without it and find out after signing                                                                                                                                                                                                                                      |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1 (fast write→read)                | Reopens the double-booking window ADR 0004 was written to close; direct-site "book now" becomes unsafe without a manual double-check step, undermining the whole "direct is source of truth" premise.                                                                                               |
| A2 (defined conflict semantics)     | A guest can pay a deposit for a night the vendor also sold on Airbnb minutes earlier. Refund, apology, and reputational cost on a single-unit property is severe — `idea-v3.md` §13 names this as a top failure mode.                                                                               |
| A3 (rate granularity)               | Orphan-gap and LOS logic has to be rebuilt as a shadow system that re-pushes derived rates on every change, defeating the "buy, wrap in an adapter" rationale and risking rate drift between what we intend and what's displayed.                                                                   |
| A4 (Postgres stays source of truth) | Forces a re-architecture where the vendor's calendar becomes authoritative, contradicting `implementation-plan.md` Phase 3 and requiring a live read-through on every quote request (latency + vendor-outage coupling on the booking path).                                                         |
| A5 (webhook + fallback)             | Falls back to iCal-class polling, which ADR 0004 already rejected as "too slow for a single-unit operator (1–4 hour drift window is catastrophic)."                                                                                                                                                 |
| A6 (cancellation propagation)       | A cancelled OTA night silently stays blocked on the direct site — lost direct-booking revenue, invisible until an owner or guest notices.                                                                                                                                                           |
| A7 (multi-currency)                 | Breaks the ICP-required USD/EUR/MXN quote display; either the vendor's settlement currency leaks into guest-facing display (confusing FX) or we must run currency conversion entirely outside the vendor, doubling reconciliation surface.                                                          |
| A8 (real guest contact)             | The north-star metric (MRT-15-P1-01) becomes structurally unmeasurable for any guest routed through the vendor — silently, not loudly, because the booking still "succeeds," it just never joins the identity graph. This is the finding most likely to be missed until Phase 6 exit criteria fail. |
| No sandbox                          | Felix cannot validate any of the above before a contract/card commitment; first real evidence arrives in production with live guest money at risk.                                                                                                                                                  |

## Acceptance evidence

- Cited source URLs in this document: **21** (distinct URLs across Hostaway, Hosthub, and the ADR 0004 carryover).
- Questions this document could **not** answer from public sources (require a sandbox trial per §3):
  1. Hostaway: conflict-resolution behavior on a direct/OTA double-booking race (A2).
  2. Hostaway: whether guest email/phone for _direct_ bookings routed through it are real addresses (not proxied) (A8, direct path).
  3. Hostaway: whether guest email/phone for OTA-originated bookings are ever the real address vs. always `hostProxyEmail`-style masking (A8, OTA path).
  4. Hostaway: exact MXN support in the `currencyCode` enum (A7).
  5. Hostaway: whether an orphan-gap-specific rate primitive exists or must be simulated via ad-hoc seasonal rules (A3).
  6. Hostaway: whether cancellations fire the same webhook SLA as creations, or only surface via polling (A6).
  7. Hostaway: existence of an official sandbox/test-mode account distinct from a live account with a demo listing.
  8. Hosthub: every assertion in the contract (A1–A8) — the public API reference is a placeholder; real capability is entirely gated behind a support conversation per ADR 0004.
  9. Hosthub: pricing tier at which API access (if any of the above turns out favorable) is included vs. requires the Pro/AI plan.
